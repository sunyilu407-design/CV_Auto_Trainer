# LLM规则生成 + Autodistill 批量标注方案分析

> 对比「当前系统」与「提案方案」，提出融合优化建议

---

## 一、当前系统 vs 提案方案 — 架构对比

| 维度 | 当前系统 | 提案方案 |
|------|----------|----------|
| **需求理解** | VLM 一次性解析（Upload → IntentConfirm），单轮 prompt→JSON | LLM **多轮对话**协商，持续细化规则 |
| **需求表达** | `class_name` + `prompt` + `negative_prompt`（CLIP 友好词） | 结构化规则 JSON（颜色范围、面积范围、空间约束、排除条件） |
| **检测引擎** | YOLO-World（零样本，CLIP 文本编码） | Autodistill + GroundedSAM（零样本，DINO+SAM） |
| **效果差时兜底** | Snowball：手标 50-100 张 → 种子训练 → 自动打标 | LLM 初标验证 → 用户纠偏 → 重新生成规则 |
| **特征提取** | VLM 从图片推理（estimated_size_hint、occlusion 等） | 后端代码从标注框提取（RGB 均值、面积、距离） |
| **用户确认** | IntentConfirm 页：静态表单编辑 class 定义 | 可视化验证：LLM 初标 + 画框 + 规则匹配说明 |
| **对话能力** | ❌ 无（一次提交，人工编辑） | ✅ 提案要求，但未给出具体实现 |

## 二、提案方案的优势（值得吸收的点）

### 2.1 🎯 多轮对话式需求确认（核心亮点）

**当前问题**：IntentConfirm 是一个静态表单页面，用户只能编辑 VLM 已经输出的字段。如果 VLM 理解偏差大，用户只能手动改文本框——但大多数用户**不知道怎么改 prompt 才能让 YOLO-World 检测得更好**。

**提案的改进思路**：引入一个"需求确认助手"，通过**多轮对话**逐步明确需求：
```
用户: "检测货车轮胎下的三角木"
助手: "我理解您要检测三角木。请确认：
       1. 三角木通常是什么颜色？（黄色/红色/木色？）
       2. 三角木大约多大？（相对画面占比？）
       3. 是否只检测贴近轮胎的？独立放置的算不算？"
用户: "黄色或红色的，只检测轮胎旁边的"
助手: "明白了。我生成了以下规则，让我在您的图片上试一下..."
       [显示带标注框的验证图片]
用户: "漏检了这个小一点的"
助手: "已将面积下限从 0.015 降到 0.01，重新检测..."
```

**优势**：
- 降低用户认知门槛：不需要理解 CLIP、prompt engineering
- 需求精度更高：通过追问细化模糊描述
- 闭环验证：规则生成 → 试标 → 反馈 → 优化，比静态表单效率高

### 2.2 📐 结构化规则的可解释性

当前系统的 `prompt` 是自然语言描述，用户不清楚它如何影响检测结果。提案的结构化规则（颜色范围、面积范围、空间约束）更加透明可控，用户能直接理解"为什么漏检了"——比如面积阈值设太高。

### 2.3 🔍 初标验证的可视化反馈

当前系统在 AlgorithmPlan 页有 YOLO-World 预览，但只展示检测框，不解释**为什么**命中或漏检。提案的 LLM 初标会给出匹配依据（如"颜色 R=240 符合范围，与轮胎距离 30px < 50px"），帮助用户判断规则是否合理。

## 三、提案方案的劣势和风险

### 3.1 ⚠️ Autodistill/GroundedSAM 的实际局限

| 问题 | 说明 |
|------|------|
| **长文本描述效果差** | GroundedSAM 的 Grounding DINO 组件和 CLIP 一样对文本敏感，长描述（如"yellow triangular object with R:230-255..."）实际效果远不如简单短语（"wheel chock"） |
| **颜色/面积等规则无法传递** | Autodistill 的 `CaptionOntology` 只接受文本描述，不支持像素级的颜色过滤或面积约束。规则中的 "R:230-255, G:170-210" 无法被 GroundedSAM 理解 |
| **部署成本高** | GroundedSAM 需要 ~8GB 显存（SAM-ViT-H + Grounding DINO），比 YOLO-World (~3GB) 大得多 |
| **速度慢** | Autodistill 单张推理 ~2-5 秒 (GPU)，1000 张需要 30-80 分钟；YOLO-World batch 推理快 5-10x |

### 3.2 ⚠️ LLM 规则的"虚假精确"

LLM 生成的"R:230-255, G:170-210"看起来精确，但实际上：
- 这些数值是 LLM 的猜测/编造，并非真正从图片中测量
- 下游没有任何引擎能直接消费这些像素级规则
- 用户看到"精确的数字"会产生虚假的信任感

### 3.3 ⚠️ LLM 初标不可靠

LLM 多模态模型（如 GLM-4V、Qwen-VL）做目标检测的坐标精度很差：
- 边界框定位误差通常 > 20%（vs YOLO-World < 5%）
- 无法批量处理，每张图需要一次 API 调用（成本 + 延迟）
- 不如直接用 YOLO-World 预览来得准

## 四、融合优化方案

**核心思路**：把提案中"多轮对话需求确认"的优势，嫁接到当前系统已验证的技术栈上。不换检测引擎，但大幅升级需求理解环节。

### 4.1 新增：需求确认助手（Requirement Negotiation Chat）

在 `IntentConfirm` 阶段新增一个**对话面板**，替代当前的纯表单编辑。

```
┌─────────────────────────────────────────────────────────┐
│  Stage 1: 需求协商                                       │
│                                                          │
│  ┌─────────────┐  ┌──────────────────────────────────┐  │
│  │  对话面板     │  │  实时规则 & 预览                   │  │
│  │             │  │                                    │  │
│  │  [AI] 我理解 │  │  类别定义:                         │  │
│  │  您需要检测  │  │  ┌─────────────────────────┐      │  │
│  │  三角木...   │  │  │ wheel_chock             │      │  │
│  │             │  │  │ prompt: "yellow wooden   │      │  │
│  │  [User] 对  │  │  │  triangular block..."   │      │  │
│  │  但只要轮胎  │  │  └─────────────────────────┘      │  │
│  │  旁边的     │  │                                    │  │
│  │             │  │  预览检测 (YOLO-World):             │  │
│  │  [AI] 明白  │  │  ┌─────────────────────────┐      │  │
│  │  已加排除条  │  │  │  [图片 + 检测框]          │      │  │
│  │  件...      │  │  │  命中: 3  漏检: 1  误检: 0│      │  │
│  │             │  │  └─────────────────────────┘      │  │
│  │  [输入框]   │  │  [重新检测]  [确认进入下一步]       │  │
│  └─────────────┘  └──────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

**对话流程**：

```
Step A: 初始理解（现有 VLM parse，不变）
  Upload 页提交后，VLM 生成初始 class 定义
  → 进入需求协商页

Step B: 多轮对话细化（新增）
  系统展示 VLM 初始理解 + 2-3 张图的预览检测结果
  → 用户看到检测效果，自然会反馈"这个不对""漏了那个"
  → AI 助手根据反馈调整 class 定义（prompt、negative_prompt、color_hint）
  → 实时重新预览，形成闭环

Step C: 规则确认
  用户满意后确认，进入 AlgorithmPlan
```

### 4.2 对话助手的技术实现

```
后端：POST /api/vlm/negotiate
请求：{
  task_id: string,
  message: string,        // 用户输入
  current_classes: VLMClass[],  // 当前类别定义
  context: {              // 上下文
    preview_results: [],  // 最近一次预览的检测结果
    conversation_history: []  // 对话历史
  }
}
响应：{
  reply: string,          // AI 回复文本
  updated_classes: VLMClass[] | null,  // 更新后的类别定义（如有改动）
  suggestions: string[],  // 建议用户接下来做什么
  should_preview: boolean // 是否建议立即重新预览
}
```

**Prompt 设计要点**：

```
你是检测需求确认助手。你的目标是通过对话帮助用户把模糊需求变成精确的 YOLO-World 检测配置。

上下文：
- 用户正在配置检测类别，当前定义如下：{current_classes}
- 最近一次检测预览结果：命中 {hit} 个，漏检 {miss} 个，误检 {false_positive} 个
- 用户反馈：{user_message}

你的任务：
1. 理解用户反馈，判断是关于漏检、误检还是其他问题
2. 调整 class 定义（主要是 prompt 和 negative_prompt）
3. 用简洁中文回复，说明做了什么调整、为什么
4. 如果改动了定义，设置 should_preview=true 让系统重新检测

注意：
- prompt 必须保持 CLIP 友好（短英文名词短语）
- negative_prompt 用来排除混淆对象
- 不要生成像素级数值（如 RGB 范围），YOLO-World 不支持
```

### 4.3 与现有系统的集成点

| 模块 | 改动 | 说明 |
|------|------|------|
| `IntentConfirm.tsx` | 重构 | 左侧加对话面板，右侧保留规则编辑 + 加入实时预览 |
| `vlm.py` | 新增 `/negotiate` | 多轮对话 API |
| `vlm_adapter.py` | 新增 `negotiate()` | 对话专用 prompt + 携带对话历史 |
| `stage2_labeler.py` | **不变** | 仍用 YOLO-World 做检测 |
| `AlgorithmPlan` | 轻微调整 | 如果需求协商阶段已做过预览，可跳过重复预览 |

### 4.4 不采用 Autodistill 的理由

| 考量 | 决策 |
|------|------|
| 显存需求 | GroundedSAM ~8GB vs YOLO-World ~3GB，很多用户 GPU 只有 4-8GB |
| 推理速度 | Autodistill 慢 5-10x，不适合实时预览交互 |
| 规则消费 | 结构化规则（颜色/面积/距离）无法传入 GroundedSAM，需要额外后处理 |
| 已有投入 | YOLO-World 管线已完整，Snowball 兜底已验证 |
| 迁移成本 | 替换检测引擎需改 stage2_labeler、worker/main、前端状态，风险大 |

**但可以作为可选后端**：如果未来遇到 YOLO-World 表现很差但 GroundedSAM 能救的场景，可在 AlgorithmPlan 阶段提供"切换检测引擎"选项。

## 五、实施路线图

### Phase 1：对话式需求协商（P0，建议优先做）

```
1. 后端 /api/vlm/negotiate 对话 API
2. 前端 NegotiationChat 组件（对话面板）
3. IntentConfirm 页重构：左对话 + 右规则编辑 + 实时预览
4. 对话 → 自动更新 class 定义 → 触发预览
```

**预期收益**：
- 用户不再需要手动编辑 prompt/class_name
- 需求确认从"看不懂的表单"变成"和 AI 聊天"
- 通过预览反馈闭环，减少后续打标和训练环节的返工

### Phase 2：结构化规则后处理（P1，可选）

```
1. 后端从标注框提取视觉特征（颜色统计、面积分布）
2. 用特征数据辅助对话助手给出更精确的建议
3. 在检测后处理中加入面积/颜色过滤（不改检测引擎，只过滤输出）
```

### Phase 3：多检测引擎支持（P2，远期）

```
1. 抽象检测引擎接口
2. 接入 GroundedSAM/Autodistill 作为可选后端
3. AlgorithmPlan 中根据场景自动推荐引擎
```

## 六、总结

| 提案要素 | 采纳决策 | 理由 |
|----------|----------|------|
| **多轮对话需求确认** | ✅ 采纳 | 核心价值点，大幅降低用户门槛 |
| **LLM 生成结构化规则** | ⚠️ 部分采纳 | 可作为对话助手的内部表示，但不暴露虚假精确的数值给用户 |
| **LLM 初标验证** | ❌ 不采纳 | YOLO-World 预览更快更准，用现有引擎做 |
| **规则可视化验证** | ✅ 采纳 | 在对话面板旁实时显示预览检测结果 |
| **用户反馈闭环** | ✅ 采纳 | 对话 → 改规则 → 重新预览 → 再反馈 |
| **Autodistill 替换 YOLO-World** | ❌ 不采纳 | 显存、速度、集成成本都不合适 |
| **Autodistill 作为可选后端** | 🔜 远期 | 特定场景下可能有价值 |
