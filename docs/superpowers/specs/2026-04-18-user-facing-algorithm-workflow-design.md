# User-Facing Algorithm Workflow Design

## 背景

当前产品主流程已经具备从需求输入到训练交付的基础骨架：

- 用户上传样板图与数据图片
- 系统解析需求并生成算法规划
- 用户进入自动打标、训练配置、训练监控与交付

但这条流程仍然保留了较强的“训练检测模型工作流”色彩，而不是“面向最终业务用户的算法定制工作流”。核心问题有三类：

- 算法规划虽然新增了，但还只是一个展示页，没有成为用户与系统讨论“这是不是我要的算法”的中枢
- 训练开始得过早，用户在真正训练前无法用业务视角验证方案效果方向是否正确
- 当前训练与交付默认是单模型心智，但真实业务方案往往是多能力组合，例如检测、跟踪、属性判断、区域规则、时序规则的组合

这使得产品虽然已经能“走通流程”，但离“让最终业务用户确认效果、再训练、再交付可直接使用算法”还有明显距离。

## 目标

本轮设计目标：

- 把主流程从“打标训练流程”升级为“需求协商 -> 算法草图 -> 离线评估 -> 训练编排 -> 算法交付”的用户工作流
- 让算法规划成为业务协商的中枢，而不是孤立的技术展示页
- 在训练前加入多段离线评估，让用户判断“这是不是我想要的算法”
- 让系统支持多模型/多能力方案，但对最终用户仍使用业务语言表达
- 交付结果从“模型文件”升级为“可直接使用的算法方案包”

## 非目标

本轮明确不做：

- 引入专业算法工程平台式的复杂 DAG 编辑器
- 面向算法工程师暴露底层模型编排细节为主的专业界面
- 在本轮设计里解决所有离线评估执行引擎的工程实现细节
- 用单一精度指标替代最终用户的业务验收

## 方案选择

采用面向最终业务用户的标准方案：

- 需求输入后先进入需求协商
- 再形成算法草图
- 再用多段离线视频做方案评估
- 用户确认效果方向正确后再进入训练编排与训练监控
- 最终交付完整算法方案包

不采用“只加一个算法规划页后直接训练”的原因是：

- 用户在训练前看不到真实业务效果
- 一旦算法草图理解偏了，后续打标与训练都会沿着错误方向投入

不采用“直接做算法工程工作台”的原因是：

- 目标用户是最终业务用户，而不是算法工程师
- 产品表达应该以业务语言为主，不应要求用户理解模型拓扑与工程细节

## 核心设计

### 1. 整体流程升级为八步用户链路

建议正式收口为以下八步：

1. 需求输入  
2. 需求协商  
3. 算法草图  
4. 多段离线评估  
5. 方案修正  
6. 训练编排  
7. 训练监控  
8. 算法交付  

这条链路的核心原则是：

- 先确认业务效果方向
- 再投入训练成本

### 2. 需求输入：从“定义模型”改为“描述业务目标”

需求输入阶段不应该要求最终用户先思考“我要什么模型”，而是让他描述：

- 想监测什么场景
- 什么情况下算触发
- 需要输出什么结果

可选输入包括：

- 样板图
- 参考框
- 历史截图

系统在这一阶段的任务不是产出训练标签，而是产出“业务目标的结构化理解”。

### 3. 需求协商：让系统和用户对齐业务意图

需求协商是新增的强制阶段，其目标是确认系统理解是否贴近用户真实需求。

页面应该以业务语言展示：

- 要识别什么对象
- 在什么区域里判断
- 满足什么时长或条件才触发
- 输出什么事件

用户需要能够直接修正：

- 监测对象
- 区域范围
- 触发时长
- 事件条件
- 输出定义

这里的重点不是让用户编辑技术配置，而是让他确认：

- 系统理解的是不是“我真正想要的业务规则”

### 4. 算法草图：把需求拆成“能力 + 规则”

算法草图不应只是展示 JSON 或技术草案，而应向用户解释系统打算如何实现该需求。

对最终用户的表达建议是：

- 这个方案包含几个识别能力
- 每个能力负责什么
- 这些能力如何组合成最终事件

例如不使用“detector/classifier/tracker”作为主表述，而使用：

- 能力 1：识别人员
- 能力 2：判断是否佩戴工帽
- 规则：当未佩戴工帽的人员进入危险区域时触发告警

这样即使方案内部是多模型、多规则，用户仍然可以基于业务目标理解它。

### 5. 多段离线评估：训练前的业务验收关口

离线评估是整条流程中的关键关口。

输入不应是单段视频，而是一组业务验证片段，至少支持：

- 应触发场景
- 不应触发场景
- 边界/混淆场景

为了降低业务用户的使用门槛，上传时可以用简单标签表达：

- 这是正常触发场景
- 这是不该触发的场景
- 这是容易混淆的场景

离线评估阶段的核心问题不是“模型指标高不高”，而是：

- 这是不是我想要的算法效果

### 6. VLM 在离线评估中的角色：业务评审官

VLM 在离线评估阶段适合承担“需求一致性评审”的角色。

它应基于：

- 已确认的需求协商结果
- 已确认的算法草图
- 用户上传的多段视频/关键帧

来判断：

- 哪些片段按业务语义应当触发
- 哪些片段不应触发
- 当前算法草图是否缺少关键能力

这意味着 VLM 的评估不是泛化的视频描述，而是带着明确的算法草图进行审查。

评估输出建议包含：

- 时间轴上的事件触发点
- 每个事件的截图或短片段
- 检测框/轨迹覆盖
- 误报候选
- 漏报候选
- 每条规则为何触发

### 7. VLM 评估不是唯一真相源

虽然 VLM 可以直接看视频并进行业务语义分析，但不建议把它定义为最终精度真相源。

产品上应将其定位为：

- 需求一致性评估

它回答的是：

- 当前算法草图是否符合用户业务意图

而不是：

- 当前模型已经达到最终上线精度

这样设计的好处是：

- 对用户解释性强
- 能在训练前发现方向性错误
- 不必把离线评估页面做成专业评测平台

### 8. 用户反馈：用业务语言回流到方案修正

离线评估之后，用户需要能够给出轻量反馈，而不是进入复杂标注流程。

建议的反馈动作包括：

- 这个触发对
- 这是误报
- 这里漏了
- 区域不对
- 时长不对

这些反馈应直接回流到方案修正阶段，用于调整：

- 事件规则
- 区域配置
- 时长阈值
- 是否需要新增辅助识别能力

这一步可以循环一次或多次，直到用户确认：

- 这就是我想要的算法

### 9. 多模型方案：从异常情况变成标准能力编排

真实业务方案往往不是单检测模型，而是多能力组合，例如：

- 检测 + 跟踪 + 区域 + 时序规则
- 检测 + 属性分类 + 区域规则
- 多对象检测 + 事件组合规则

因此系统内部的算法草图应明确支持：

- 单能力方案
- 多能力方案
- 多规则组合方案

但对最终用户的表达仍应是业务语言，而不是底层模型编排图。

页面不需要直接展示“一个 detector、一个 classifier、一个 tracker”，而是应展示：

- 基础识别能力
- 辅助识别能力
- 事件规则与组合逻辑

### 10. 训练编排：训练的是“方案中的可训练能力”

在多模型场景下，训练阶段不能再默认是“训练一个模型”。

应调整为：

- 方案中的可训练能力列表
- 每个能力是否需要训练
- 每个能力的训练状态
- 哪些部分只是规则或配置，无需训练

对最终用户的界面建议表达为：

- 基础识别能力
- 辅助识别能力
- 规则与区域配置

而不是把所有工程术语直接暴露给用户。

### 11. 训练监控：从单进度条升级为方案级监控

训练监控页需要从“单模型训练状态”升级为“整套方案的构建状态”。

用户应该能看到：

- 主能力训练中
- 辅助能力训练中
- 规则配置处理中
- 方案组装中
- 交付包生成中

这样用户理解的是“算法方案正在形成”，而不是某个孤立模型的内部训练过程。

### 12. 算法交付：交付完整方案包，而不是单个权重

最终交付物不应再仅仅是模型文件。

建议交付为完整算法方案包，包括：

- 一个或多个模型文件
- 规则配置
- 区域配置
- 事件定义
- 使用说明
- 示例输入输出

最终用户拿到的应是：

- 可直接使用的算法

而不是：

- 需要二次理解和组装的训练产物

## 涉及范围

这一轮是产品流程设计升级，后续实现大概率会涉及：

- `frontend/src/pages/Upload.tsx`
- `frontend/src/pages/IntentConfirm.tsx`
- `frontend/src/pages/AlgorithmPlan.tsx`
- 新增需求协商页
- 新增离线评估页
- 新增方案修正页或在现有页内形成循环
- `frontend/src/pages/TrainingMonitor.tsx`
- `frontend/src/pages/Delivery.tsx`
- `frontend/src/store/taskStore.ts`
- `frontend/src/api/backend.ts`
- `backend/routers/algorithm.py`
- `backend/services/algorithm_planner.py`
- 新增离线评估相关服务/路由
- 新增方案编排与交付结构描述

## 测试策略

后续实现阶段建议按以下层次验证：

1. 需求协商结果可被用户修改并回流到算法草图
2. 多段离线评估任务可创建、读取和回写用户反馈
3. VLM 评估输出结构化时间轴、证据片段和误报/漏报候选
4. 多能力方案在训练编排页可拆成多个训练单元
5. 交付页可展示完整算法方案包而非单一模型文件

产品验收标准应包含：

- 用户能在训练前看懂并确认效果方向
- 用户能在离线评估中指出误报、漏报、区域问题和时长问题
- 多模型方案不会在 UI 上退化成不可解释的技术细节
- 最终交付物符合“直接可用的算法方案包”心智

## 风险与取舍

### 风险 1：流程变长

取舍：增加了需求协商、离线评估和方案修正阶段，但换来的是训练前确认方向正确，能减少无效训练与返工。

### 风险 2：VLM 评估存在主观性

取舍：将其定位为需求一致性评估，而不是最终精度基准。它用于帮助用户判断方向是否正确，而不是替代最终上线验收。

### 风险 3：多模型方案会抬高系统复杂度

取舍：系统内部接受复杂度提升，但面向用户持续使用业务语言表达，把复杂度收敛在编排层而不是暴露给最终用户。

### 风险 4：离线评估可能诱导用户认为“已经训练完成”

取舍：需要在产品文案中明确区分：

- 离线评估验证的是算法方向与业务一致性
- 最终训练决定上线效果和稳定性
