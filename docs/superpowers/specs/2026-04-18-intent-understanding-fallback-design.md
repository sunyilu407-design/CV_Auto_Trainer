# Intent Understanding Fallback Design

## 背景

当前产品主流程已经从“只生成检测类别”扩展到“根据用户需求生成业务策略与算法草案”：

- 上传样板图与业务描述
- 通过 VLM 解析视觉目标候选
- 结合用户描述生成算法规划
- 继续进入训练配置、训练监控与交付

但当前 Stage 1 仍然存在两个明显问题：

- `VLM /api/vlm/parse` 一旦失败，整个流程被硬阻断，用户即使已经提供了足够清晰的业务描述，也无法继续生成策略草案
- 前端页面文案仍然强调“检测意图”“检测类别”“训练提示词”，与现在“按业务需求生成策略方案”的产品方向不一致

这导致两个后果：

- 产品韧性不足，单点依赖 VLM 的 JSON 返回质量
- 用户认知错位，以为系统只是在帮他训练检测模型，而不是在理解业务需求并生成完整方案

## 目标

本轮设计目标：

- 当 VLM 解析失败时，不中断主流程，允许系统基于用户文字需求继续生成初步策略/算法草案
- 把 Stage 1 和意图确认页的产品语义从“检测训练导向”调整为“需求理解/策略生成导向”
- 让错误提示从底层异常文本变成用户可理解、可行动的产品提示
- 保留 VLM 成功时的视觉增强能力，但不再把它作为唯一入口

## 非目标

本轮明确不做：

- 重写 VLM 提示词协议或引入新的模型提供商
- 新增完整的“纯文本目标抽取”独立服务层
- 大规模改造算法规划逻辑
- 删除现有目标候选编辑能力

## 方案选择

采用“降级继续”的方案：

- VLM 成功时，沿用现有路径，输出视觉目标候选并进入确认页
- VLM 失败时，不阻断流程，而是记录失败状态与原因，进入“确认需求理解”页面
- 算法规划页始终允许继续，只是在没有视觉目标候选时主要依赖用户文字需求生成草案

不采用“失败即阻断”的原因是：

- 用户已经提供了业务描述，系统没有必要因为视觉解析失败而完全停止
- 当前产品目标是生成业务策略与算法方案，而不是仅生成检测类别

不采用“显式双模式切换”的原因是：

- 会增加不必要的交互复杂度
- 当前阶段更适合把“视觉增强是可选项”内化到同一流程里

## 核心设计

### 1. VLM 失败从硬错误改为结构化降级状态

当前 `/api/vlm/parse` 在解析失败时直接抛出 500，前端只能显示原始异常：

- `VLM 解析失败，已重试 3 次: Expecting value: line 1 column 1 (char 0)`

这类信息暴露了底层 JSON 解析异常，但没有告诉用户实际发生了什么。

新的返回语义应区分：

- `success`：VLM 成功返回可用的视觉目标候选
- `failed`：VLM 失败，但接口仍返回结构化失败信息，前端据此进入降级路径

失败信息至少包含：

- `status`
- `message`
- `retryable`
- `raw_vlm_response`（可选，供调试或后续扩展使用）

面向用户的错误文案应翻译为产品语言，例如：

- VLM 返回了空内容或非 JSON 内容
- VLM 已响应，但返回格式不符合系统要求
- VLM 服务暂时无法完成视觉理解，当前将先根据文字需求生成草案

### 2. 前端显式建模“视觉解析状态”

当前前端基本只有 `vlmResult`，默认认为“有结果”或“无结果”。

这不足以表达以下几种不同状态：

- 还未发起解析
- 解析成功
- 解析失败但已切换到降级模式

前端状态模型需要至少补充：

- `vlmStatus: idle | success | failed`
- `vlmErrorMessage: string | null`
- `vlmFallbackMode: boolean`

设计要求：

- `vlmStatus=success` 时，保留现有目标候选编辑体验
- `vlmStatus=failed` 时，不能再把页面表现成“没有上下文”，而要明确提示“当前草案主要基于文字需求”
- 降级状态也必须允许进入后续算法规划

### 3. Stage 1 从“上传样板图 + 描述”改成“输入业务需求”

当前上传页仍然把样板图与参考框描述为必须步骤，且按钮文案是“解析意图”。

新的页面语义应调整为：

- 主标题：输入业务需求 / 描述你的监测目标
- 副标题：系统会先理解你的业务需求，再结合样板图补充视觉细节，生成策略草案
- 样板图区域：可选视觉参考，不是唯一入口
- 主按钮：生成需求理解 / 生成策略草案

输入区示例要从“训练检测模型”导向切换到“业务场景”导向，例如：

- 识别仓位是否被货箱占用，持续 10 秒后输出占位事件
- 识别人员进入 A 区、离开 A 区，并在从 A 区进入 B 区时输出跨区事件

错误提示区改成双层表达：

- 第一层说明视觉解析未完成
- 第二层说明系统将先基于文字需求继续生成初步草案

### 4. 确认页从“确认检测意图”改成“确认需求理解”

当前 [IntentConfirm] 页面展示的是“检测类别”和“页面展示用中文描述”，默认语义仍然是“训练检测模型前的类别确认”。

新页面目标是确认系统对业务需求的理解结果，因此应拆成两种展示路径：

#### A. VLM 成功

- 页面标题改为“确认需求理解”
- 副标题强调“系统对目标、区域、事件和视觉线索的理解”
- 目标卡片继续保留，但标题改为“候选监测对象”或“候选视觉目标”
- 继续允许用户修正中文展示描述

#### B. VLM 失败

- 顶部显示明显但非阻断的告警条
- 告知用户：视觉解析失败，当前理解结果主要基于文字需求生成
- 不展示空的类别卡片
- 改为展示一份简明摘要：
  - 用户原始需求
  - 系统推断的场景类型
  - 关键区域
  - 关键事件
  - 关键时长/持续条件

这让确认页真正承担“需求理解确认”的角色，而不是仅确认类别名。

### 5. 算法规划页接受“无视觉目标候选”的上下文

当前算法规划逻辑已经基本允许 `vlm_result` 为空，但前端流程仍然默认“没有 VLM 结果就缺少上下文”。

本轮要明确：

- 没有 VLM 结果不等于没有任务上下文
- 只要有用户描述，就应允许生成算法规划

算法规划页文案改为：

- 把业务需求扩展成可交付的策略与算法草案

在 `vlmStatus=failed` 时，页面应显示提示：

- 当前草案主要基于文字需求生成，后续仍可补充视觉参考

### 6. 后端错误文本归一化

当前最常见的失败之一是模型返回空字符串或非 JSON 内容，从而触发 `json.loads` 异常。

根因层面可能不同，但产品层面应收敛成少数几种统一错误：

- 空响应
- 非 JSON 响应
- JSON 结构不符合约定
- 上游 HTTP 调用失败

这样前端不需要理解底层异常类型，也避免把 `Expecting value: line 1 column 1` 一类技术细节直接暴露给用户。

## 测试策略

本轮采用 TDD，至少覆盖以下场景：

1. VLM 返回空字符串或非 JSON 内容时，后端不再返回原始 JSON 解析异常给前端，而是返回结构化失败信息
2. 前端在 `vlmStatus=failed` 时仍可继续进入后续策略/算法规划链路
3. 算法规划接口在没有 `vlm_result` 时，仍能基于 `user_description` 生成草案
4. 上传页与确认页的新文案构建后保持通过

集成验证至少包括：

- `./.venv/bin/python tests/test_integration.py vlm-parse-settings`
- 新增的 VLM 降级解析测试
- `cd frontend && npm run build`

## 风险与取舍

### 风险 1：降级路径会降低视觉目标的准确性

取舍：接受初版草案可能更粗，但优先保证业务流程可继续；同时在 UI 明确标注当前结果主要基于文字需求。

### 风险 2：确认页在成功/失败两种模式下会出现双态 UI

取舍：保留这种分支，因为两种上下文信息量确实不同；通过统一标题和统一下一步按钮维持整体连续性。

### 风险 3：后端如果只是吞掉异常，可能掩盖真实诊断信息

取舍：对用户暴露归一化错误文本，但在返回体或日志中保留必要的调试字段，避免可观测性丢失。
