# Phase 2 第二轮设计：训练推荐解释层与复杂度细化

## 背景

Phase 2 第一轮已经完成以下能力：

- 后端可以根据算法规划、用户默认设置、运行时能力生成 richer `training_recommendation`
- 算法规划接口会返回 `recommended_config`、`reason_summary`、`source_map`
- 前端训练配置页会用推荐结果做默认预填
- 用户手动修改后的字段不会被后续推荐静默覆盖

当前还存在两个明显问题：

1. 用户在训练页上虽然拿到了推荐值，但看不清每个字段为什么会是当前值
2. 后端复杂度判断仍然偏粗，`model / imgsz / epochs / patience` 的推荐区分度不够

第二轮只解决这两个问题，不扩到更重的设备探测或部署目标推荐。

## 目标

本轮目标分为两部分：

### 1. 训练页解释层

让用户在训练页上能一眼看清：

- 当前关键字段来自哪里
- 哪些字段已经被用户手动修改
- 系统为什么给出当前推荐

### 2. 场景复杂度细化

让后端推荐器对算法复杂度的判断更细一层，并且把影响集中在最容易理解的字段上：

- `model`
- `imgsz`
- `epochs`
- `patience`

## 非目标

本轮不做以下内容：

- 不新增真实硬件探测或更深的浏览器/系统能力采集
- 不做部署目标导向推荐
- 不把推荐升级为硬约束
- 不改训练启动 API
- 不把 `lr0 / conf / iou` 也一起做复杂场景自适应

## 产品规则

### 优先级

训练字段显示优先级：

1. 用户手动修改
2. 推荐来源标签
3. 系统默认兜底

只要用户手动改过某个字段，这个字段在 UI 上就应该优先显示为“已手动修改”，而不是继续显示“算法推荐”或“环境推荐”。

### 本轮覆盖字段

第二轮只要求对以下字段做来源展示：

- `model`
- `trainMode`
- `exportFormats`
- `imgsz`
- `epochs`
- `patience`

## 前端设计

## 顶部推荐总览卡

保留当前推荐卡的基础结构，但补齐两类信息：

- 推荐摘要：直接显示更自然的中文原因说明
- 推荐来源摘要：列出几个关键字段的来源

建议展示格式：

- `模型：算法推荐`
- `训练模式：环境推荐`
- `导出格式：环境推荐`

## 字段级来源标记

在关键字段旁边增加来源 badge。

建议固定使用以下标签：

- `算法推荐`
- `环境推荐`
- `用户默认`
- `系统默认`
- `已手动修改`

颜色不需要重新发明一套视觉语言，直接沿用现有 badge/token 风格即可。

## 前端状态模型

本轮不新增一份独立的“字段来源状态”。

页面展示时直接由两份已有状态派生：

- `trainingRecommendation.source_map`
- `trainConfigOverrides`

展示逻辑：

1. 如果 `trainConfigOverrides[field] === true`，显示 `已手动修改`
2. 否则如果 `source_map[field]` 存在，按来源映射显示中文标签
3. 否则显示 `系统默认`

这样可以避免 store 冗余，也能保证用户改动优先级最高。

## 后端设计

## 复杂度模型

第二轮不引入复杂规则引擎，只把现有复杂度拆成更可解释的几个维度：

- `target_count`
- `rule_count`
- `tracking_required`
- `temporal_or_region_intensity`

其中 `temporal_or_region_intensity` 的含义是：

- 只有区域规则：低强度
- 只有时序规则：中强度
- 同时有区域与时序规则：高强度

## 推荐规则细化

### model

- 单目标、低复杂度：`yolo11s.pt`
- 多目标，或跟踪 + 规则叠加：`yolo11m.pt`

本轮不继续推荐更重模型，避免系统过度激进。

### imgsz

- 普通复杂度：`640`
- 多目标或复杂规则：`1280`

### epochs

- 低复杂度：`100`
- 中复杂度：`120`
- 高复杂度：`140`

### patience

- 低复杂度：`20`
- 高复杂度：`30`

### 不调整的字段

本轮以下字段仍然保持稳定默认值：

- `lr0`
- `conf`
- `iou`

原因是这些字段解释成本高、用户理解门槛更高，本轮优先解决高价值且易解释的推荐项。

## 推荐说明文案

后端输出的 `reason_summary` 改成自然中文句子，而不是英文片段拼接。

目标风格：

- `当前任务包含 2 个目标类别，且需要跟踪与持续时序规则，因此推荐使用 YOLO11m、1280 图像尺寸和更高训练轮次。`
- `当前任务为单目标基础监测，复杂度较低，因此推荐使用 YOLO11s 和标准训练配置。`

这样前端可以直接复用，不需要再次做业务翻译。

## 数据兼容性

第二轮不破坏第一轮的数据结构，继续保持：

- `recommended_config`
- `reason_summary`
- `source_map`
- 旧兼容字段：`recommended_model / train_mode / export_formats`

这样已有页面和旧任务数据仍然可以加载。

## 测试策略

## 后端测试

新增或扩展测试验证：

- 单目标低复杂度场景推荐 `yolo11s / 640 / 100 / 20`
- 多目标或 tracking + 规则叠加时推荐升级到 `yolo11m / 1280 / 120+ / 30`
- `reason_summary` 输出中文可读说明
- `source_map` 仍然稳定可用

## 前端测试/验证

至少通过构建与现有集成验证证明：

- 推荐解释卡能读取新中文摘要
- 字段级来源标签能正确区分“推荐来源”和“已手动修改”
- 用户修改字段后再次应用推荐，不会覆盖用户值

## 成功标准

第二轮完成时应满足：

- 训练页能明确显示关键字段来源
- 用户手动修改后，UI 会明确提示该字段已被覆盖
- 后端复杂度推荐比第一轮更细，且只影响容易理解的关键字段
- `reason_summary` 变成中文自然说明
- 第一轮已有验证不被破坏
